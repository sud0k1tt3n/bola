# Обоснование подхода

## Почему YOLO11n
* **Скорость на CPU.** 2.6 млн параметров, ~6.5 GFLOPs при 640 px: один кадр на обычном
  CPU обрабатывается за доли секунды — с огромным запасом к требованию «≤ 30 с», без GPU
  на стороне заказчика.
* **Быстрое дообучение.** Transfer learning с COCO-весов; на 3 класса хватает сотен–тысяч
  размеченных кадров и нескольких часов на одной GPU. Весь цикл «разметка → обучение →
  экспорт» — одна библиотека (ultralytics), что важно для команды из 6 человек и срока 1–1.5 мес.
* **Почему 11, а не v8.** По данным Ultralytics на COCO YOLO11n точнее YOLOv8n (mAP 39.5
  против 37.3) при меньшем числе параметров и вычислений; API и формат разметки те же.
  Вернуться на v8 — одна переменная `RHD_BASE_WEIGHTS=yolov8n.pt`.
* **Путь к бортовому исполнению.** Экспорт в ONNX / OpenVINO / TensorRT без переписывания кода.
* **Альтернативы.** Сегментация (U-Net, YOLO11-seg) точнее для подтоплений — у воды нет
  чётких границ, прямоугольник её плохо описывает. Для MVP выбрана детекция как более
  быстрая в разметке; переход на `-seg` меняет только detector.py и формат полигонов.

## Почему такой маппинг severity
| Класс | Уровень | Логика |
|---|---|---|
| flooding | красный | глубину воды по снимку не оценить; безопасное допущение — проезда нет |
| bridge_collapse | красный | разрушение переправы = разрыв маршрута |
| fallen_tree | жёлтый | часто объезжается или убирается силами экипажа; требует внимания, но не закрывает маршрут |

Статус кадра — худший из найденных: хотя бы один красный → красный. Маппинг зашит в
`config.SEVERITY` намеренно: это решение предметной области, а не параметр модели.
Порог для подтопления снижен (0.35 против 0.40): пропуск опаснее ложной тревоги.

## Геопривязка
Надирная модель: центр кадра = GPS, размер на земле = `2·H·tan(FOV/2)`, поворот на курс,
перевод метров в градусы локальной аппроксимацией. Пиксель → нормированные координаты →
билинейная интерполяция по четырём углам footprint. Один и тот же пересчёт используется
для кадра и для bbox, поэтому на карте они согласованы. Корректность проверена тестами
(длины сторон по гаверсинусу, азимуты на верх и правый край кадра при разных yaw).

## Ограничения
1. **Камера должна смотреть в надир.** При наклоне подвеса > 10° footprint — трапеция,
   модель прямоугольника даёт ошибку (API выдаёт предупреждение). Решение — полная
   проекция с pitch/roll.
2. **Плоский рельеф.** Холмы и обрывы искажают масштаб. Решение — ортотрансформирование по DEM.
3. **Точность высоты — главный источник ошибки.** Ошибка высоты на 10% = ошибка размеров
   footprint на 10%. `GPSAltitude` обычно над уровнем моря; для не-DJI бортов высоту над
   землёй лучше вводить вручную.
4. **Точность GPS БАС** — единицы метров (без RTK); это нижняя граница точности привязки.
5. **Bbox грубо описывает протяжённые объекты** (подтопленный участок дороги, поваленное
   по диагонали дерево) — площадь завышается. Решение — сегментация или oriented bbox (YOLO11-OBB).
6. **Данные.** Публичных аэроснимков обрушенных мостов очень мало — это главный риск
   качества класса `bridge_collapse` (см. data/README.md).
7. **Один кадр — одно решение.** Нет сшивки в ортофотоплан и учёта перекрытий между кадрами.
